## Executive summary

The strongest explanation for a fast-rising **Supabase egress** meter is the image delivery path. The CMS uploads original files, and the public site serves those originals directly to visitors. The homepage HTML referenced 25 unique Supabase images totalling **6,962,335 bytes (6.96 MB)** by response headers, including one 1.63 MB JPEG. This is the sum of the referenced files, so a visitor who downloads only the initial viewport may transfer less. If the meter is **stored GB**, the main risks are full-size files, duplicate uploads and objects that remain after failed cleanup. The supplied dashboard confirms the uncached egress overage at organization level.

Googlebot is allowed by the live robots policy. The public HTML sample had readable content and self-referencing canonicals across the main content types. The site has two clear search visibility gaps. Its main navigation routes several commercially important topics to pages marked **noindex**, and the sitemap silently drops entire content sections when Supabase queries fail. The live sitemap listed 257 English URLs. Google Search Console access is needed to tell which URLs Google discovered, indexed, clustered under another canonical, or chose to exclude.

## What the project does

This is a Next.js App Router site deployed on Vercel, with an English public storefront and a Supabase-backed staff CMS. Visitors browse tours and itineraries, destinations, experiences, accommodations and blog articles, and can submit enquiries. The repository also contains routes for safari packages, national parks, the fleet, and seasonal travel. The portal manages publishing, translations, media, site settings and enquiries. PostgreSQL stores CMS content and media metadata. The public Supabase `media` bucket stores files. The browser uploads each file to Storage, then inserts the separate `media_assets` row. Public pages and the portal reuse those files in hero slides, cards, galleries and image previews.

## Supabase findings

| Priority | Finding | Evidence and consequence |
| --- | --- | --- |
| High | **Original uploads double as public delivery files.** | The bucket migration permits images up to 10 MiB. The upload function passes the original file through, with no resizing, compression, output-size budget or thumbnail generation. Next.js image optimization is disabled globally. Its configuration records a deliberate trade-off to avoid Vercel image transformations. The same URL can supply a full-width hero, a small card or a staff thumbnail. The Kenya tour filter returned 80 unique direct Supabase image URLs in the HTML. That is a count of references, and individual browser transfers depend on lazy loading and scrolling. |
| High if the limit is cached egress | **Cache hits still serve the full original and count toward the cached egress allowance.** | Three homepage assets returned `Cache-Control: public, max-age=31536000` and `CF-Cache-Status: HIT` on repeated GETs. HEAD returned private/no-cache and DYNAMIC for those same URLs, so it was used for sizing only. For scale, 1,000 sessions each fetching the full measured homepage image set would consume about 6.96 GB of image transfer before other pages. This is an illustration. Actual usage depends on lazy loading, repeat visitors, cache behavior and request mix. |
| High if the limit is stored bytes | **Duplicate and unused assets accumulate.** | Every upload generates a new random object path. The application has no content-hash deduplication or reuse check at upload time. The picker supports intentional reuse, but uploading the same file again creates another copy. Replacing an image reference or deleting content does not automatically reclaim the old file. I found no scheduled inventory or cleanup process in the repository. The metadata row also lacks size, dimensions and a content hash, making bulk review harder. The number of duplicates and unused files in production is unknown. |
| Medium | **The media row and object can get out of sync.** | Upload creates the object before the database row. If row creation fails, rollback attempts to delete the object and ignores the cleanup result. Browser interruption can strand the object between operations. Deletion removes the row first, so a later Storage failure can leave a billable file missing from the media library. Some galleries store IDs in JSON and some settings store public URLs directly, so the database cannot enforce all references. The deletion comment also assumes Open Graph foreign keys clear automatically, while the repository definitions use ordinary references without an explicit delete action. |
| Medium | **Dynamic content can add Supabase API egress separately from images.** | Sampled tour, destination, experience, accommodation and blog details sent private, no-store HTML responses. Tour metadata and page content query Supabase separately, and tour pages also request related tours. The code caches some shared inputs. An audit of actual request counts and PostgREST response bytes is needed to measure this component. HTML cache headers provide evidence about the page response only. |

**How to identify the exhausted meter.** Match the warning and billing interval in Supabase Usage. For **cached or uncached Storage egress**, group Storage request bytes by object path and cache status and compare the top paths with hero, card and gallery URLs. For **stored GB**, reconcile a read-only object inventory against the media table and CMS references, including JSON galleries and raw URLs. For **database/API egress**, inspect the PostgREST breakdown and public rendering traffic. For a **single failed upload**, compare the file size with the bucket and project upload limits. The Vercel transformation threshold mentioned in the repository is a separate quota. ## SEO findings

| Priority | Finding | Evidence and consequence |
| --- | --- | --- |
| High | **Major search intents lead to intentionally non-indexable filters.** | The navigation offers Kenya safaris, Tanzania safaris, and combined itineraries through tour query parameters. The listing metadata marks query-string variants `noindex, follow` and canonicalizes them to the generic listing. I verified this live for `/en/tours?country=kenya` and `/en/destinations?country=kenya`. Filtering itself is valid. The gap is that these menu entries lack dedicated indexable destinations within this route structure, so the generic catalogue and individual tours have to carry those broader commercial intents. |
| High | **Sitemap failures can look like successful responses.** | `safeRows()` converts a Supabase error or exception to an empty result. The index then omits the section and the XML route can still return HTTP 200. A transient database problem, bad join or missing permission can therefore hide a group of live pages from sitemap discovery until a healthy refresh. Queries are also unpaginated, so their coverage can eventually hit the Supabase API row cap. The live largest section had 103 entries and there is no evidence of truncation at the observed size. |
| Medium | **Sitemap placement has a Search Console dependency.** | The six child sitemaps live under `/sitemaps/` but list URLs under `/en/`. Google documents directory-level sitemap scope unless submitted via Search Console. The root index and children all returned HTTP 200. Search Console submission and processing status were outside this audit. |
| Medium | **Some public routes are empty or incomplete and can still be crawled.** | The live sitemap excludes the fleet, national parks, safari packages and travel-by-month routes. All four returned HTTP 200. Travel by Month renders the explicit “Content coming soon” placeholder with a generic description and no canonical in the sampled HTML. The fleet landing page contains substantive vehicle and guide information and a gallery. The current sitemap ties its inclusion to published fleet detail records, so an eligible standalone page is omitted even when it has useful content. Some park content already has a valid home under Destinations, so the absent national-parks sitemap is consistent with an empty separate section and does not establish that park guides are missing from Google. |
| Medium | **Transient content failures can be exposed as missing pages.** | Tour metadata selects `data` without distinguishing a Supabase error from a genuinely missing row, then calls `notFound()`. The content data path has a similar null branch. A nonexistent tour correctly returned HTTP 404 in the live sample. I did not trigger a database failure, so a false 404 is a code-level failure mode. |
| Medium | **The Google publishing hook uses an API for unsupported content.** | The code attempts to send ordinary tour, article and other detail URLs to the Google Indexing API when credentials exist. Google limits this API to eligible job postings and livestream events. The code also ignores the endpoint response status, so the CMS can offer no reliable indexing feedback through this call. Production credentials and actual usage were unverified. |
| Medium | **Image weight and dynamic rendering are performance risks.** | The homepage returned about 337 KB of decoded HTML and referenced 6.96 MB of unique Supabase originals. The unfiltered tour catalogue returned about 469 KB of decoded HTML and the Kenya tour filter about 437 KB. These are HTML body and asset-header measurements, separate from compressed wire sizes and actual mobile load behavior. Core Web Vitals field data, mobile LCP, INP and CLS remain unverified. |
| Low / intentional | **Several audit crawlers are blocked by policy.** | The live robots file explicitly blocks AhrefsBot, AhrefsSiteAudit, SemrushBot and SiteAuditBot along with several other crawlers. Their limited coverage can be expected under this policy. Googlebot falls under the permissive default group for the public catalogue. Google-Extended appears in a separate blocked group. |

## What remains to establish

- **Index coverage.** Compare sitemap URLs in Search Console’s Page Indexing report by route family. Inspect samples from “Discovered – currently not indexed,” “Crawled – currently not indexed,” alternate canonical and noindex categories. Compare the last crawl, rendered HTML, Google-selected canonical and referring page. This distinguishes discovery problems from indexing decisions.
- **Ranking and content.** Search Console Performance by query and landing page is needed to identify weak ranking among already-indexed pages. The live catalogue has 103 tour URLs and 84 accommodation URLs alongside three blog articles in the sitemap. That mix warrants a page-by-page review of tour overlap, itinerary specificity, and the links between guides and related commercial pages. Counts alone cannot diagnose ranking. Backlinks, local search visibility and competitive positions were outside the verified scope.
- **Usage.** Obtain the exact Supabase quota name and project-level bytes for the billing period. Confirm stored objects, cache status and requests by path before attributing the limit to any one cause. Field performance should be assessed separately from the raw payload sample.

The sampled public pages meet Google’s basic technical eligibility requirements. The findings above explain where specific pages can lose crawl discovery or eligibility and where heavier media can affect experience. Google weighs relevance and other ranking signals after it has discovered and indexed the page. ## Verification on 26 November 2026

- The destination database has 244 published English records and 1,464 published translations across French, German, Spanish, Italian, Swahili and Chinese. Each language has 103 tours, 84 accommodations, 34 destinations, 20 experiences and three articles. The package and national park translation tables have no published English records. Publication counts establish coverage at the record level.
- The local homepage returned HTTP 200 in all seven languages. All nine rendered section headings differed from English in each translated version. The contact planning radio option highlighted in the screenshot was present in the selected language in all six translated responses. All five legal pages returned HTTP 200 in all six translations, including four successful retries during development. The policy dictionaries contain 387 source strings each and preserve the internal Markdown link destinations.
- The migration manifest contains 875 JPEGs, 318 WebPs, 43 AVIFs, 11 PNGs and eight GIFs. Of those 1,255 objects, 1,026 had a one-year cache lifetime and 229 had a one-hour lifetime. The original usage screenshot shows 7.777 GB uncached egress and 0.222 GB stored. Future quota usage depends on traffic, cache misses and database response sizes.
- The live homepage HTML transferred 63,630 compressed bytes. One request completed in 0.59 seconds with 0.53 seconds to first byte, and the header check showed a Vercel cache hit. Two independent mobile-viewport browser runs recorded largest contentful paint of 13.69 and 1.92 seconds. The faster run identified the homepage hero JPEG as the largest element. These are lab measurements. The public PageSpeed endpoint returned HTTP 429, so field Core Web Vitals remain unverified.
- The local implementation serves the nine existing homepage slides as content-hashed WebP assets and defers later slides. Their combined source files weighed 2,280,768 bytes, compared with 593,326 bytes across the mobile variants and 1,525,122 bytes across the desktop variants. New JPEG uploads are resized and converted to WebP when the result is smaller. Other existing images retain their original formats.
- The production switch, verification of all detail routes with the destination public key, root document language and Search Console exclusion-reason breakdown remain release checks. Search Console indexing must be assessed after publication.
